## Context

Sections 10.1 to 10.4 of `spec/lot-2.md`: the first half of the MCP OAuth flow. An MCP client discovers the Worker, registers itself, sees the Worker's own consent page, and the user logs in at the fake Google provider of ticket 07; only invited users get an authorization code.

## Decided spec

- The discovery documents (10.1), `POST /register` (10.2), `GET /authorize` and the consent page, `POST /authorize/consent` (10.3), `GET /callback` with the ID token checks, the access control and the 403 refusal page (10.4); the Google refresh token stored encrypted (6.3).
- The log events `auth.client.registered`, `auth.oauth.completed` and `auth.oauth.denied` (section 12).

## Acceptance criteria

- Worker tests (Google's endpoints answered by a stub): each error case of 10.2 and 10.3 in its order, with redirects only where 10.3 allows them; the consent page shows the client name as escaped text and has two `<button type="submit" name="decision">`; `deny` returns `access_denied`; `approve` redirects to Google with every parameter of 10.3; a bad `state`, a bad signature, a wrong `aud` and a wrong `nonce` at the callback are refused; an invited user and the admin get a code and a `users` row with the right role; a non-invited user gets the 403 page and no row; no stored value holds the Google refresh token in clear.
- E2E tests: E2E-29 of section 13 (`api` project); the consent page then the fake Google sign-in page lead an invited user back to the client with a code, and E2E-02 (`browser` project). The `browser` tests run in CI; where Chromium cannot be installed, `./scripts/check.sh e2e` skips them (section 3.1).
- `./scripts/check.sh all` passes, and the CI run is green with the five jobs.

## Out of scope

The token endpoint (next ticket) and `/mcp` (ticket 10); PATs, sessions, consent memory, rate limiting.
