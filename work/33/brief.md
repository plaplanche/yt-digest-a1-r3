## Context

Sections 10.5 and 10.6 of `spec/lot-2.md`: the second half of the OAuth flow. The client exchanges its code with PKCE for tokens bound to the `/mcp` resource and refreshes them with rotation and reuse detection; the Worker can tell whether a bearer is a valid access token. The next ticket protects `/mcp` with that check.

## Decided spec

- `POST /token` for both grants (10.5): form-encoded only, PKCE S256, `resource`, the order of the checks, single-use codes, rotation, families and reuse detection, `Cache-Control: no-store`.
- The access token check of 10.6, the user read again on every request.
- The log events `auth.token.issued` and `auth.refresh.reuse_detected` (section 12).

## Acceptance criteria

- Worker tests: each error of 10.5 (unknown client, wrong verifier, used code, expired code, other client, other `redirect_uri`, missing parameter, wrong `resource`, unknown grant, a body that is not form-encoded); a code is used up by a failed exchange; `Cache-Control: no-store`; a refresh rotates both tokens and keeps earlier access tokens valid; the reuse of a used refresh token gives `invalid_grant` and revokes its family, access tokens included.
- Worker tests of the 10.6 check: a valid access token is accepted; an expired or revoked one, a refresh token, a node token and the token of a user whose invite was revoked are not.
- An e2e test (`api` project, the login done over HTTP through the consent form and the fake Google's `login_hint`): E2E-31 of section 13, the family's revocation shown at `/token`.
- `./scripts/check.sh all` passes.
